# Vercel Deployment

## Context

- The app runs locally on SQLite through `@prisma/adapter-better-sqlite3` (`src/prisma/prismaClient.ts`), with `prisma/dev.db` (dev, e2e) and `prisma/test.db` (action tests).
- Vercel functions have a read-only, ephemeral filesystem and cannot load the native `better-sqlite3` module reliably, so a local `.db` file cannot be the production database.
- Passkeys (spec 015) are bound to the domain: `src/actions/auth/config.ts` reads `WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGIN` and defaults to `localhost`, which fails in production.
- Migrations are applied today with `prisma migrate deploy` / `prisma migrate dev` against a `file:` URL (`prisma.config.ts`, `tests/actions/globalSetup.ts`).
- The owner does **not** want to change database engine or data model. The database stays SQLite; only where it lives changes.

## Goals

The repository is deployable to Vercel as-is. After this spec, the only manual steps left are the ones no code can do (creating a Turso database, importing the repo in Vercel, pasting two secrets), and they are documented step by step. Local dev, Storybook, Vitest and Playwright keep working on local SQLite files, with the existing `prisma/dev.db` and `prisma/test.db` untouched and no local workflow change (`npm run dev`, `prisma:migrate`, `test`, `test:e2e`).

## Requirements

### Database: Turso (libSQL, SQLite-compatible)

- Production uses **Turso** (hosted libSQL). `provider = "sqlite"` in `prisma/schema.prisma` does not change. Models, migrations and generated client shape do not change.
- Dependencies (explicit exception to "no new packages"): add `@prisma/adapter-libsql`. Remove `@prisma/adapter-better-sqlite3` and `better-sqlite3`: libSQL handles `file:` URLs too, so dev, tests and prod share one code path. Existing `.db` files are plain SQLite and keep working. No other package.
- `src/prisma/prismaClient.ts` builds `PrismaLibSql` from env:
  - `DATABASE_URL`: `libsql://…` in production, `file:./prisma/dev.db` locally (default kept), `file:./prisma/test.db` in action tests.
  - `TURSO_AUTH_TOKEN`: optional, passed as `authToken`; required only for `libsql://` URLs.
- The client is created once and reused across hot reloads in dev (module-level singleton on `globalThis`) so serverless and `next dev` do not open a new connection per import.
- Remove `serverExternalPackages: ["@prisma/adapter-better-sqlite3"]` from `next.config.ts` and the `better-sqlite3` entries in `vitest.config.ts` `server.deps.external`, unless the libSQL packages need the same treatment. Read `node_modules/next/dist/docs/` for `serverExternalPackages` before deciding.
- `src/generated/prisma` is regenerated by `npm run prisma:generate`, never hand-edited. Commit the regenerated output as the repo already does.

### Migrations on Turso

- `prisma migrate deploy` cannot target a `libsql://` URL. Add `scripts/migrate.ts` (Node 22 runs `.ts` natively; no `tsx`, no new package) that:
  - reads `prisma/migrations/*/migration.sql` in name order;
  - connects with `@libsql/client` (installed with the adapter) using `DATABASE_URL` and `TURSO_AUTH_TOKEN`;
  - records applied migration names in its own table (`_migrations`: `name` unique, `appliedAt`) and skips those already applied;
  - runs each pending migration in a transaction and exits non-zero on the first failure;
  - is idempotent, so it is safe on every build.
- Local databases stay managed by Prisma Migrate (`npm run prisma:migrate`, `tests/actions/globalSetup.ts` unchanged). The script therefore **skips with exit 0 when `DATABASE_URL` is a `file:` URL**, unless called with `--allow-file` (used only by the script's own tests, on a temp file). This guarantees `npm run build` and `npm run db:migrate` locally never touch `dev.db`.
- New migrations are still authored with `npm run prisma:migrate`; the same `migration.sql` files are what the script applies on Turso.
- npm script: `"db:migrate": "node scripts/migrate.ts"`.

### Build and install

- `package.json`:
  - `"postinstall": "prisma generate"` so Vercel always has a fresh client.
  - `"build": "npm run db:migrate && next build"` so every deploy applies pending migrations before the app starts. Preview deployments must not migrate the production database: the script cannot tell which database is production, so the rule is that Preview gets its own `DATABASE_URL` (see Env vars) and the README says so.
  - `"engines": { "node": "22.x" }` (the migrate script relies on native TypeScript execution).
- No `vercel.json` unless something cannot be expressed in `package.json` or the dashboard. Vercel auto-detects Next.js.
- `export const dynamic = "force-dynamic"` stays on routes that read the DB or cookies. No `revalidatePath`, no `router.refresh`, no Route Handlers (AGENTS.md).

### WebAuthn on Vercel

- `src/actions/auth/config.ts` resolves `rpID` and `origin` in this order:
  1. `WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGIN` when set (explicit override, custom domain).
  2. On Vercel: `VERCEL_PROJECT_PRODUCTION_URL` when `VERCEL_ENV === "production"`, else `VERCEL_URL` (preview). `rpID` is the host without scheme, `origin` is `https://` + host.
  3. Otherwise `localhost` / `http://localhost:3000`.
- With no manual variable, the default `*.vercel.app` production URL works for passkeys out of the box. Documentation states that changing the domain later invalidates existing passkeys.
- The `session` cookie is already `Secure` when `NODE_ENV === "production"`; no change.

### Env vars

- `.env.example` documents every variable with a comment: `DATABASE_URL`, `TURSO_AUTH_TOKEN`, `WEBAUTHN_RP_ID`, `WEBAUTHN_ORIGIN`. `.env` stays gitignored.
- Vercel variables to set by hand (documented): `DATABASE_URL`, `TURSO_AUTH_TOKEN`. Scope them per environment: **Production** points at the production Turso database, **Preview** points at a separate Turso database (`workout-preview`), never the production one. Previews therefore migrate and write only to the preview database.
- No secret is committed. No secret is read in client code.

### Documentation

- Add a `## Deploy to Vercel` section to `README.md`, copy-pasteable, in this order:
  1. Install the Turso CLI and log in (`turso auth signup` / `turso auth login`).
  2. `turso db create workout-prod`, then `turso db show workout-prod --url` and `turso db tokens create workout-prod`.
  3. Repeat with `workout-preview` for the Preview environment.
  4. Push the repo to GitHub, Vercel → *Add New → Project* → import.
  5. Set `DATABASE_URL` and `TURSO_AUTH_TOKEN` per environment (Production → `workout-prod`, Preview → `workout-preview`), then *Deploy*. The first build creates the schema; production starts empty.
  6. Optional: custom domain → set `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGIN`, redeploy.
- Production starts with an empty database: local data is not migrated.
- Update the README stack list: SQLite via libSQL, Turso in production.
- Update the AGENTS.md "Stack" line and "Backend" section to mention libSQL/Turso and `scripts/migrate.ts`, keeping the Next.js block at the bottom untouched.

### Verification

- `npm run build` succeeds locally with `DATABASE_URL=file:./prisma/dev.db`.
- `npm test` (storybook, components, actions) passes on libSQL `file:` URLs.
- `npm run test:e2e` passes against `prisma/dev.db` through the libSQL adapter.
- Add action-level tests in `tests/actions/` for the migrate script's core logic (idempotent second run applies nothing; a failing migration rolls back and exits non-zero; a `file:` URL without `--allow-file` is skipped) against a temp `file:` database, not `test.db` or `dev.db`.
- Manual smoke test after first deploy is listed in the README: register a passkey, create a workout, sign out and back in, redeploy and confirm the data is still there.

## Out of scope

- Importing existing local data into production.
- Hosting Storybook.
- Changing the data model, Prisma provider, or moving to Postgres.
- Creating the Turso database, the Vercel project, or setting secrets (accounts and credentials are manual).
- Custom domain purchase and DNS.
- CI pipelines, GitHub Actions, monitoring, backups, analytics, and edge or middleware changes.
- Rate limiting or other hardening beyond spec 015.
